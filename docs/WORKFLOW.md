# 科研与工程工作流

## 1. 日常开发循环

1. 从 `STATUS.md` 获取当前任务。
2. 在 `TASKS.md` 核对依赖、验收与停止条件。
3. 从 `SOURCE_REGISTRY.md` 和 `DECISION_LOG.md` 获取依据。
4. 建立独立分支；修改前运行现有测试或文档检查。
5. 代码功能采用测试先行；实验采用预注册协议。
6. 产出完成后运行全部相关检查。
7. 更新任务、状态、进度、实验、决策、风险和交接入口。
8. 只提交本任务相关文件，不提交数据、密钥或大型产物。

## 2. 任务状态

- `BLOCKED`：依赖或官方信息缺失，不能安全执行。
- `READY`：依赖齐全，可以开始。
- `IN_PROGRESS`：唯一当前任务。
- `DONE`：完成标准全部满足且有证据路径。
- `STOPPED`：触发停止条件，保留现状和原因。
- `DEFERRED`：明确推迟，不阻塞当前Gate。

任何时刻最多一个核心技术任务为 `IN_PROGRESS`。

## 3. 新证据工作流

1. 保存原始文件或稳定链接，不覆盖旧版本。
2. 计算文件哈希并登记检查日期。
3. 在 `SOURCE_REGISTRY.md` 分配证据ID。
4. 标记其为官方、宣讲、本地事实或待核实假设。
5. 检查是否冲突现有决策。
6. 如需改变方案，在 `DECISION_LOG.md` 追加“替代”记录，禁止修改历史记录。

## 4. 实验工作流

1. 在 `EXPERIMENTS.md` 预注册实验ID、问题、数据、指标、预算和停止条件。
2. 冻结配置、代码提交和数据指纹。
3. 运行前执行数据泄漏检查。
4. 运行并同步资源账本、SwanLab和私有审计日志。
5. 无论成功失败都登记结果。
6. 只在满足 `EXPERIMENT_PROTOCOL.md` 时形成结论。

## 5. 分支与评审

- `main`：仅保存已验证、可恢复的稳定状态。
- 每个任务使用独立分支 `task/<task-id>-<short-name>`。
- 合并前必须运行该任务验收命令，并更新文档。
- 不强制队友修改核心模块；低风险任务通过独立文件或结果表交付。

## 6. 团队边界

- 技术负责人 + Codex：架构、核心闭环、评测协议、集成和最终审查。
- 队员A：Docker、依赖、资源与运行说明。
- 队员B：SwanLab、故障注入、回滚和演示流程。
- 队员C：数据统计、时间划分、结果表和独立复现。
- 队员共同负责PPT、计划书、视频和答辩题库 `[L-TEAM-001]` `[D-014]`。
